## Preview workflow and memory limits
- Use Compose preview rendering to inspect and fix UI against the annotated reference before relying on emulator verification. Render only the screen/component and state currently being changed, one render at a time; do not batch all screen previews.
- Scrollable screens must be inspected through the actual document bottom. Android Studio's expand-content preview control can make the preview much taller than the emulator. Use that control where accessible; a device-height image is not evidence of the full document.
- If the tool cannot operate expand-content, use a single targeted tall preview fixture at the reference width and sufficient content height, and explicitly verify the last content boundary. Preserve separate fixed-viewport verification of pinned headers/actions/navigation; do not stretch the production viewport just to pass a screenshot check.
- Stop unused preview refreshes and close/release unused preview surfaces before moving to the next target where IDE controls are available. Drop retained tool-image references when no longer needed. Do not retain a gallery of live renders or rerender unchanged fixtures. Current MCP exposes render by file/function/index but no close/release/expand command; do not falsely claim those IDE actions were executed through MCP.
- Keep Studio's existing4GiB heap cap. Avoid concurrent previews/builds, render storms, and increasing heap to hide allocation problems. If preview memory pressure recurs, stop rendering and inspect the actual process/error before retrying; do not claim that smaller fixtures alone prove a heap fix.
- Keep emulator checks for IME, rotation/recreation, scroll persistence, real mutations and navigation. Preview success alone does not prove those behaviors.
- Push successful build checkpoints occasionally, with unresolved fidelity/behavior items left explicit. This workflow is part of the user's2026-11-10 goal update and applies throughout the remaining plan.
