# Phase 5 data ownership and release contract

## Module audit
No package shuffle was needed. Rules, SQL/schema and portable snapshot code live in shared/commonMain. Android SQLiteOpenHelper, reminder/file adapters live in data. iOS SQLite driver stays in iosMain. App owns file pickers, restore confirmation and navigation; feature modules own screens/ViewModels. Core-ui owns the reusable coin badge and mint controls.
New paths: shared/data/sql/{GameBackup,BackupDigest}.kt; data/BackupService.kt; app/presentation/ui/DataSettingsScreen.kt. Existing GameDatabase/GameStorage gain snapshot methods; SqlGameDatabase delegates to the shared engine. No duplicate DTO or persistence owner was introduced. verifyArchitecture rejects feature-to-feature dependencies/ViewModel imports and Android/Java imports in commonMain.

## Portable format 1
Extension .mamxanh; MIME application/octet-stream. UTF-8 with strict decoding. Header is MAMXANH/1, newline, lowercase SHA-256 of payload, newline, payload. SHA-256 detects corruption; it does not encrypt or authenticate the file.
Payload is a sequence of length-prefixed cells: decimal UTF-16 code-unit length, colon, text; -1: means SQL NULL. Empty string is 0:. It starts with schema integer, app version, creation UTC epoch milliseconds, table count. Each table has its allowlisted name, column count, ordered column names, row count, row-major nullable cells. No file paths or SQL from the archive are executed. Limits: 16 MiB input, 100,000 total rows, 128 columns/table, 1,000,000 code units/cell while parsing, followed by a stricter 16,384-code-unit gameplay-field limit before import; exact end-of-payload required. App-version labels are limited to 80 characters.
All 34 registered tables, including sqlite_sequence, are included. Tasks/schedules/windows, occurrences, timer/focus sessions and intervals, wallet/receipts, inventory/equipment, trees including hidden neglect/fertilizer/death, care/growth history, plots, layout/sections, discoveries/rewards, preferences/reminder definitions, memories/notes/reflections are preserved. OS grants and pending AlarmManager handles are excluded.
Format 1 currently accepts schema 7 only. Older app database schemas upgrade through GameSchema before export. Future formats require explicit readers/migrations, never best-effort dropping fields.

## Replace-all restore
Read through SAF with bounded input. Verify header, checksum, lengths, schema/table/column identity; import into an isolated in-memory SQLite database with foreign keys enabled. Validate gameplay invariants there. Display timestamp/version/counts and explain replacement, privacy and historical dead-tree implications. On explicit confirmation, write an AtomicFile safety snapshot in noBackupFilesDir; only then replace live rows in a single SQLite transaction. Any database error rolls back all changes. Restore identifiers and high-water sequences so deleted IDs cannot be reused. Same snapshot restored twice yields the same rows and assets.
GameStorage emits repository invalidation only after commit; observers reload derived state. The Android replacement adapter explicitly cancels displayed notifications and rebuilds pending reminder identities even when restored UI values compare equal. Post-commit OS scheduling failures are logged without misreporting the committed replacement as a rollback. Current-time growth simulation can advance an old tree snapshot after restoration; this is normal gameplay, not fabricated restore data. The raw snapshot is exact at commit.
A latest local safety copy is available for explicit recovery; recovery retains it. Clearing data has two confirmations and also creates the safety copy. Uninstall deletes it. SAF cancellation makes no change.
No routine silently repairs/deletes history. Invalid archives are rejected. Legacy log-backed occurrences can legitimately reference removed tasks and remain auditable.

## Migration checklist
Schema 1–3: legacy task/tree/inventory/meta/logs and plot addition. Schema 4: finite task contracts, occurrences, ledger, timers. Schema 5: timed lifecycle and removal of ml reservoir. Schema 6: engagement/reminders/history. Schema 7: garden layout, collections and finite sections.
Numbered GameSchema migrations remain authoritative. PhaseFiveBackupTest reconstructs every supported version 1–7 and checks stable task/tree IDs, old growth and grandfathered wealth. Existing Phase 1–4 tests cover deeper gameplay conversions. Never downgrade a database to rollback an app.

## Localization
Phase 5 screen copy uses Vietnamese default resources with prepared values-en translations. Enabling English as a shipping locale requires completing the legacy resource migration first.

## Privacy and store copy
Mầm Xanh is a single-player habit garden. No account is required. Primary tasks, history and garden data are stored locally. Optional local notifications need permission. Backup/diagnostic export happens only after the user chooses a document location. Backups are unencrypted and may expose private history. Diagnostics omit task text, notes, balance, tree state and persistent user/device identifiers.
The app contains optional Ktor networking infrastructure and INTERNET permission. Do not claim zero collection solely from offline gameplay or this source audit. Recheck configured API_BASE_URL, dependencies, actual release network traffic and any future crash SDK before completing Play Data Safety declarations. Android OS/device backup behavior must be disclosed separately from user-controlled export.
Store listing draft: “Build gentle habits and grow a personal garden offline. Complete small tasks, use optional focus timers and care for your trees. No mandatory account. Export and restore your own backup files.” Use screenshots from the actual release candidate; no payment/Exclusive purchase claims.

## Versioning, signing and rollout
Application ID remains com.mamxanh.app. Debug/verification IDs are never store artifacts. The Phase 5 internal build is 0.2.0 / versionCode 2, upgrading the 0.1.0 / code 1 baseline. The release owner must assign a strictly increasing production version code for every upload. Set MAMXANH_KEYSTORE, MAMXANH_STORE_PASSWORD, MAMXANH_KEY_ALIAS and MAMXANH_KEY_PASSWORD outside the repository. Run `:app:bundleRelease -Pmamxanh.versionCode=<next-code> -Pmamxanh.versionName=<release-version>`. preReleaseBuild rejects missing signing credentials or explicit versions; it cannot fall back to debug signing. Never commit a keystore/password. Key custody and actual store upload remain release-owner gates.
Before publication: configure signing custody and contact/privacy URL, review OSS notices/assets rights, run fresh install and upgrade on physical low/midrange devices, verify airplane mode, denied notifications, reboot, clock/timezone changes, SAF provider failures, TalkBack and large text. Check measured cold start, completion latency and repeated tree-screen memory; emulator observations are not universal budgets.
Publish internally first, then staged rollout. Require green core CI reports and artifacts; a workflow definition is not a passing CI result. On regression stop rollout, preserve backups and ship a forward-compatible fix; never replace live data with an older schema. iOS UI/store release is outside this phase; native compilation is portability evidence only.
